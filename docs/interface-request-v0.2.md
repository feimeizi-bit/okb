# 接口需求单 v0.2

> 中文名：接口需求单（B 提给 A 的"我需要你给我什么"清单）
> 提出方：B（数据与评分线）　接收方：A（评测框架线）
> 提交日：__________　期望确认日：__________（建议提交日 + 2 天）
> 状态：待 A 逐条确认

---

## 0. 这份单子怎么用（三步）

1. B 填好第 2 节的表格（已预填，改改即可），发给 A
2. A 在最后一栏逐条填 **确认 / 做不到 / 改成这样**；凡填"改成这样"的，B 要再看一遍并回复
3. 双方确认完，把结果抄进 `docs/CONTRACT.md`，在群里各说一句"v0.2 冻结"，流程结束

**优先级含义**

| 优先级 | 含义 |
|---|---|
| 必须 | 没有它，评分管线无法正常工作或结果不可信 |
| 最好有 | 没有它也能跑，但会丢分或限制样本设计空间 |

---

## 1. 背景（给 A 看的一页）

赛题的"自动评分能力"和"数据设计质量"两项共占 **50%**，全部依赖 A 侧产出的**运行证据**。
B 的评分程序要读 A 的证据文件，B 的测试样本要被 A 的引擎执行 —— **两边对接的地方就叫接口**。
接口一旦各自定义，就会出现"你写的字段叫 anchors，他读的字段叫 anchor_list"这类事故，导致几十条样本全部返工。

这份单子就是把这些对接点一次性定死。

## 2. 需求清单

| 编号 | 我需要什么 | 验收标准（做到什么程度算满足） | 不给我会怎样 | 优先级 | A 的回复 |
|---|---|---|---|---|---|
| I-1 | 证据流水 `evidence.jsonl`，每条证据有唯一编号和定位字段 | 一行一个 JSON；字段齐全：`id / run_id / seq / ts / task_id / session_id / turn / source / type / actor / payload / raw_ref`；`id` 形如 `ev_r001_000102`，同一 run 内不重复 | 评分结论无法回指具体证据，"可解释"这项直接丢分 | 必须 | |
| I-2 | 每款 Agent 声明自己能提供哪些证据 | 接口 `capabilities()`，对 **对话 / 记忆 / 文件 / 工具** 四项各返回「有」或「无」 | 某款 Agent 没有记忆后端时，评分整批报错，而不是自动降级 | 必须 | |
| I-3 | 记忆快照 `probe_memory()` | 每个任务**开始前**和**结束后**各导出一次；JSON 数组，含 键、值、写入时间、来源 | 分不清"正确地没记住"和"忘了记"，边界识别维度全错 | 必须 | |
| I-4 | 支持多会话 | 样本里能写 `session: s1 / s2`；程序按顺序执行，**换会话时清空对话上下文**（记忆保留） | "长期保持"这一维根本没法测（跨会话才叫长期） | 必须 | |
| I-5 | 每次运行的 `manifest.json` | 记录：Agent 版本、**Agent 配置文件名与内容哈希**、模型名与版本、temperature、随机种子、起止时间、数据集版本、判官版本 | "稳定性与可复现性"15% 拿不到；"导入不同配置批量对比"无法追溯是哪个配置 | 必须 | |
| I-6 | 结果目录结构固定 | `runs/<run_id>/` 下固定放 `manifest.json`、`evidence.jsonl`、`verdicts.jsonl`、`report/`、`raw/` | 引擎和评分脚本反复对路径，纯浪费时间 | 必须 | |
| I-7 | 抽象动作映射表 `action_map` | B 的样本里写 `file.write(订单.yaml)` 这类**抽象动作**；A 负责翻译成每款 Agent 的真实调用。映射表单独成文件、可编辑 | 样本会绑死在 KylinBot 上，"通用性"15% 丢分 | 最好有 | |
| I-8 | 记忆注入通道可选 | 样本里能指定 `injection: dialogue / memory_api / file_drop`。其中 **dialogue 必须支持** | 只能靠"直接写入记忆库"构造的样本（如"用户分三次提到同一偏好"）造不出来 | 必须 | |
| I-9 | 每个任务有状态，失败的不算扣分 | `task.status ∈ {ok, timeout, agent_error, env_error}`；非 ok 的任务标为 **invalid**，从能力统计中剔除，但在报告里单列数量 | 环境抽风会被算成"模型忘了"，分数被污染且无法解释 | 必须 | |
| I-10 | 每次运行有独立的记忆与文件空间 | 每个 run 使用独立记忆库路径 + 独立工作目录；并发批量时互不干扰；`reset()` 必须恢复到干净基线 | 批量对比时两款 Agent 共享记忆，整批结果作废 | 必须 | |
| I-11 | 保留原始证据，不只保留摘要 | `runs/<run_id>/raw/` 保留：完整 LLM 请求与响应、工具调用参数、文件写入前后内容 | 判官与人工复核只能看摘要，可解释性打折；答辩被追问细节答不上来 | 必须 | |
| I-12 | 证据脱敏 | 身份证号、手机号等敏感值落盘时**掩码或存哈希**；原文只存在于内存与 Agent 侧 | 我们测"敏感信息不该被持久化"，自己的评测日志里却存着敏感号，答辩被抓很难看 | 必须 | |
| I-13 | 离线可复现 | 一次真实 run 的证据可**离线重放**（回放模式）；判官结果可缓存复用，缓存键 = 证据哈希 + 判官版本 | 评审现场断网或模型 API 故障，演示当场翻车 | 最好有 | |

## 3. 三条最难理解的，单独解释

**I-9 为什么"失败的任务不能算扣分"**
评测会跑很多轮，环境总有抽风的时候（网络超时、Agent 崩溃）。如果一次超时被记为"模型没记住"，你的分数就不可信了 —— 而且事后无法解释。所以任务必须带状态，非 `ok` 的直接剔除出统计，但在报告里单独列出"无效任务数"，这本身就是稳定性的证据。

**I-11 为什么"摘要不够"**
`evidence.jsonl` 是归一化后的摘要，方便程序读。但当判官判错、或者评委问"你怎么确定这条记忆真被写进去了"，只有摘要就答不上来。原始请求响应必须留着，这是"可解释"的底气。

**I-13 为什么"离线"是保命项**
演示视频和答辩都在现场进行，网络和模型 API 是你们控制不了的。有回放和缓存，出问题还能继续演示；没有，就只能等网络恢复。

## 4. 流程约定

| 项目 | 约定 |
|---|---|
| 确认方式 | A 在本表最后一栏逐条填 确认 / 做不到 / 改成这样；凡"改成这样"需 B 复核 |
| 冻结期 | 从确认日起第 10 天之后，接口**只允许新增字段，不允许改名或删除**；新增须在 CONTRACT.md 记一笔 |
| 变更通知 | 任何字段变更必须同时通知对方，并在 CONTRACT.md 的变更记录里加一行 |
| 争议处理 | 当天升级给负责人（__________）拍板，**不隔夜** |
| 记录落点 | 本单确认结果 → 抄进 `docs/CONTRACT.md` |
